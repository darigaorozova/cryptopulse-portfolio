# CryptoPulse: Data Platform for a Neobank Crypto Feature

Final project for a Data Engineering course, by Dariga Orozova.

The project is an end-to-end data platform for a neobank that operates in 6 EU countries, with pilots in Kyrgyzstan and Kazakhstan. Customers trade crypto, and the team needs daily reporting on trades, fees and KYC status. The platform loads these sources into PostgreSQL, transforms them through staged layers, publishes a ClickHouse mart and a live dashboard, and streams KYC status changes via CDC.

## What it does

- **Sources:** daily trade files (~313 trades per day), a customer file, crypto prices from the CoinGecko API, and a change stream of KYC statuses.
- **Orchestration:** two Apache Airflow DAGs. The first loads one date at a time; the second builds the marts.
- **Layers in PostgreSQL:** `stg` (raw data as text) → `ods` (typed, keyed, upserted) → `datamart` (daily and monthly marts).
- **Data quality:** 8 checks on the ODS layer and 6 on the marts. A failed check stops the DAG.
- **dbt:** 3 staging models and 1 mart built with `ref()`, plus 15 tests. A singular test checks that the dbt mart matches the mart built by Airflow.
- **CDC:** Debezium captures changes in `users_kyc`, Kafka transports them, and a JDBC sink applies them to the ODS layer. Latency is under 10 seconds.
- **Analytics:** a ClickHouse mart and an HTML dashboard rebuilt after each run.

## Results

- 120 days of history (01.07–28.10.2026), all runs green.
- 37,577 trades and 3,000 customers.
- CoinGecko API usage is about 2% of the monthly quota per day; a 120-day backfill uses about 7%.

## Stack

Python · Apache Airflow 2.10 · PostgreSQL · ClickHouse · dbt 1.8 · Debezium · Apache Kafka · Kafka Connect

## Limitations

- Trades and customers are synthetic, generated by `data/generate_data.py` with deliberately messy records. Crypto prices are real, from CoinGecko.
- No secrets are stored in the repository. Passwords come from environment variables, and the CoinGecko key is stored in an Airflow Connection.
